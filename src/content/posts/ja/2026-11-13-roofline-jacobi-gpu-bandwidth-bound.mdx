## 演算性能は15倍なのに、速さは4.5倍だった

カタログ上の演算性能が15倍のGPUへPoissonソルバーを移しました。結果は4.5倍でした。カーネルを書き直しても、キャッシュをうまく使っても4.5倍から動きません。奇妙なのはここからです。4.5は二つのデバイスのメモリ帯域の比と小数点まで一致します。本記事では、この一致が偶然ではないことを示します。ルーフラインモデル(roofline model、演算性能とメモリ帯域のうち低い方が速度を決めるというモデル)でJacobiスイープの限界を計算します。読み終えるころには、GPU移植の前に期待できる高速化を紙の上で見積もれるようになります。

## 2020年のノートの3行

2020年2月のノートには、CPUとGPUの違いが3行で書かれています。CPUは、ランダムなメモリアクセスや制御フロー(分岐・ループ条件)を含む汎用演算に向いています。GPUは、大量のデータに同じ演算を繰り返すデータ並列演算に向いています。そして、GPUのメモリ帯域はCPUより高いです。例として挙げた数字は180 GB/s対40 GB/sでした。

最も重要なのは3行目です。前の2行は「GPUが得意な仕事」を述べています。3行目は「その仕事がどこまで速くなるか」の上限を述べています。CFDのステンシル演算(stencil、周囲の格子点いくつかで1点を更新する計算)はデータ並列の典型です。だからGPUによく合います。しかし、どれだけ速くなるかは帯域が決めます。

## ルーフライン:性能は二つの天井の低い方

カーネルの実効性能 $P$ は次の式で抑えられます。

$$
P = \min\left(P_{\text{peak}},\; I \cdot B\right), \qquad I = \frac{\text{FLOP}}{\text{byte}}
$$

$P_{\text{peak}}$ はデバイスのピーク演算性能(FLOP/s)、$B$ はメモリ帯域(byte/s)です。$I$ は演算強度(arithmetic intensity、DRAMから1バイト取ってくるごとに行う演算数)です。

両対数グラフでは、この式は傾いた直線と水平線が交わる屋根の形になります。交点 $I^* = P_{\text{peak}}/B$ をリッジポイント(ridge point)と呼びます。$I < I^*$ なら演算器がデータを待ちます。これをメモリ律速(memory-bound)と呼びます。$I > I^*$ ならデータは十分で、演算がボトルネックです。これを演算律速(compute-bound)と呼びます。

本記事のデバイスモデルは、ノートの帯域をそのまま使い、ピーク性能は仮定しました。CPUは40 GB/s、300 GFLOP/sです。GPUは180 GB/s、4,500 GFLOP/sです。リッジポイントはCPUが7.5、GPUが25.0です。$I < 7.5$ のカーネルは両デバイスとも帯域しか見ません。その高速化は $180/40 = 4.5$ 倍です。

## Jacobiスイープ1回が運ぶバイト数

2次元Poisson方程式 $-\nabla^2 u = f$ のJacobi更新は次のとおりです。

$$
u^{k+1}_{i,j} = \tfrac14\left(u^k_{i-1,j} + u^k_{i+1,j} + u^k_{i,j-1} + u^k_{i,j+1} + h^2 f_{i,j}\right)
$$

$h$ は格子間隔、$k$ は反復番号です。セル1つあたり加算4回、乗算1回です。収束判定用の $|\Delta u|$ の比較1回を加えて6 FLOPと数えます。

バイト数はキャッシュの再利用で変わります。隣接4点と $f$ を毎回DRAMから読み、結果を書くと倍精度で $6 \times 8 = 48$ バイトです。キャッシュが隣接値を再利用すれば、$u$ の読み込み、$f$ の読み込み、$u^{k+1}$ の書き込みだけが残り24バイトです。演算強度はそれぞれ0.125と0.25です。どちらもCPUのリッジポイント7.5より30倍以上小さいです。キャッシュをどれだけうまく使っても、このカーネルはメモリ律速から抜け出せません。

ここで反復回数が入ってきます。総時間は「スイープ1回の時間 × スイープ数」です。スイープ数はハードウェアではなくアルゴリズムが決めます。Jacobiのスペクトル半径は $1 - \pi^2 h^2/2$ 付近です。格子を2倍にするとスイープ数は理論上4倍、本記事の判定基準では約3倍になります。

## コード:実際にスイープを数え、二つのデバイスに時間を割り当てる

下のコードは単位正方形で $-\nabla^2 u = 1$ をJacobiで解きます。スイープ数は実際に数え、時間はルーフラインの式で割り当てます。バイト数だけが異なる6種類のカーネルを比較します。時間ブロッキング(temporal blocking、キャッシュに載せたタイルで $k$ 回のスイープを続けて回し、DRAM往復を $1/k$ に減らす手法)と、毎スイープのPCIeコピーも入れました。

```python
import numpy as np

# デバイスモデル: 元ノートの帯域(40 vs 180 GB/s) + 仮定したピーク演算性能
DEV = {"CPU": (40e9, 300e9), "GPU": (180e9, 4500e9)}   # (B/s, FLOP/s)
PCIE = 12e9                                            # ホスト<->GPU コピー帯域

def jacobi_sweeps(n, tol=1e-6):
    """単位正方形 -∇²u = 1, u=0 境界。max|Δu| < tol までの Jacobi スイープ数。"""
    h2 = (1.0 / (n - 1)) ** 2
    u = np.zeros((n, n))
    for it in range(1, 10**6):
        new = 0.25 * (u[:-2, 1:-1] + u[2:, 1:-1] + u[1:-1, :-2] + u[1:-1, 2:] + h2)
        du = np.abs(new - u[1:-1, 1:-1]).max()
        u[1:-1, 1:-1] = new
        if du < tol:
            return it

def roofline_time(cells, sweeps, flops, bytes_, dev, pcie_bytes=0.0):
    bw, peak = DEV[dev]
    per_sweep = cells * max(flops / peak, bytes_ / bw)
    return sweeps * (per_sweep + cells * pcie_bytes / PCIE)

FLOPS = 6.0   # セルあたり: 加算4 + 乗算1 + |Δu| 比較1
KERNELS = [   # (名前, セルあたりDRAMバイト, セルあたりPCIeバイト)
    ("naive (no reuse)", 48.0, 0.0),
    ("cached u,f,u_new", 24.0, 0.0),
    ("temporal block k=4", 24.0 / 4, 0.0),
    ("temporal block k=32", 24.0 / 32, 0.0),
    ("temporal block k=128", 24.0 / 128, 0.0),
    ("cached + PCIe copy/sweep", 24.0, 16.0),
]

for n in (32, 64, 128):
    print(f"N={n:4d}  sweeps={jacobi_sweeps(n):6d}")

n = 64
sweeps = jacobi_sweeps(n)
cells = (n - 2) ** 2
print(f"\nN={n}, sweeps={sweeps}, ridge CPU={300/40:.1f}  GPU={4500/180:.1f} FLOP/B")
print(f"{'kernel':26s} {'AI':>6s} {'CPU ms':>8s} {'GPU ms':>8s} {'speedup':>8s}  bound(GPU)")
for name, b, pb in KERNELS:
    ai = FLOPS / b
    tc = roofline_time(cells, sweeps, FLOPS, b, "CPU") * 1e3
    tg = roofline_time(cells, sweeps, FLOPS, b, "GPU", pb) * 1e3
    bound = "memory" if ai < 4500 / 180 else "compute"
    if pb: bound = "PCIe"
    print(f"{name:26s} {ai:6.3f} {tc:8.3f} {tg:8.3f} {tc/tg:8.2f}  {bound}")
print(f"\npeak FLOP ratio = {4500/300:.1f}x, bandwidth ratio = {180/40:.2f}x")
```

## 4.50が4回、15.00と0.41が1回ずつ出た理由

naive、cached、k=4はすべて4.50倍です。バイトを48から6へ8分の1にしたら、両デバイスの時間がちょうど8分の1になりました。比は変わりません。メモリ律速の領域では、バイトの節約が両デバイスに公平に効くからです。

k=32ではAIが8になります。CPUはリッジポイント7.5を超えて演算律速になります。GPUはまだ帯域の領域です。そのため比は4.80へ少し上がります。k=128でAIが32になると、GPUもリッジポイント25を超えます。比はピーク演算性能比15.00に達します。ただし、128回のスイープをキャッシュ上で続けて回す時間ブロッキングは現実的ではありません。タイル境界のゴースト領域がブロッキングの深さだけ大きくなるからです。この行は「15倍にはこれだけの演算強度が要る」という目盛りとして読むべきです。

最後の行は0.41倍、つまりGPUが2.4倍遅いです。毎スイープ、フィールドをホストへ送って受け取ると、セルあたり16バイトが12 GB/sのバスを通ります。このバスはCPUのメモリより遅いです。ホストで収束判定するために毎回コピーするコードは、まさにこの罠にはまります。判定に必要な最大値だけをGPU上でリダクション(reduction、配列を1つの値にまとめる演算)して持ってくれば、このコストは消えます。

最初の表のN=32、64、128の行は、スイープ数が1,176 → 3,720 → 10,537と増えることを示しています。格子を2倍にするとセルは4倍、スイープは約3倍になります。デバイスを替えて得る4.5倍は、格子を一段細かくするだけですぐに食いつぶされます。

## 帯域の壁の前で打てる三つの手

一つ目は、バイトを減らすことです。倍精度を単精度に変えると、セルあたりのバイトが半分になります。メモリ律速のカーネルはその分だけ速くなります。反復法の内部だけ単精度で回し、残差は倍精度で計算する混合精度がよくある妥協です。

二つ目は、演算強度を上げることです。時間ブロッキングのほかにも、高次ステンシルや行列フリー(matrix-free)の高次DGカーネルは同じデータでより多く計算します。こうしたカーネルはGPUのリッジポイント側へ移動します。そこから先で、ピーク演算性能比が意味を持ち始めます。

三つ目は、スイープ数そのものを減らすことです。マルチグリッド(multigrid)はスイープ数を格子サイズにほぼ依存しなくします。これはデバイス交換で得る4.5倍よりはるかに大きいです。同じ結論をAmdahlの観点から見た記事があります([ホットスポット比率pを決めるのは許容誤差](/ja/posts/2026-11-11-python-hotspot-amdahl-poisson-share/))。陰解法で反復回数を決める別の要因は[LU-SGSのCFL収束限界](/ja/posts/2026-11-06-lu-sgs-factorization-error-cfl-limit/)で扱いました。

## GPU移植の見積書の1行目に書く数字

カーネルごとにセルあたりのFLOPとセルあたりのバイトを数えて割ります。その値が両デバイスのリッジポイントより小さければ、期待できる高速化は帯域比です。演算性能比は見積書に書きません。次に、毎反復ホストとやり取りするバイトがあるかを確認します。一つでもあれば、そのバスの帯域が新しい天井になります。この2行で、移植前に4.5倍なのか0.4倍なのかが分かります。
