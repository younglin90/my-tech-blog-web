## C コードを Fortran に移したら、格子サイズで速度がばらついた

2020 年 2 月、C コードと Fortran コードを 1 本のプログラムに統合する作業をしました。当時のメモは短いものです。「CPU は任意のメモリアクセスに強い。GPU は帯域幅が高い。」実際にぶつかった問題は、その 2 行の間にありました。C の二重ループをそのまま Fortran に移しました。結果は正しかったのです。しかし格子 200 では速く、格子 256 では目に見えて遅くなりました。

この記事では、その原因をキャッシュシミュレータで直接数えます。結論を先に書きます。ループ順が間違っていれば遅くなるのは確かです。ただし、いつ遅くなるかは格子サイズが決めます。そして 2 のべき乗のサイズは特に危険です。読み終えると、ループ順と配列パディング(padding、配列の宣言サイズをわざと 1 つ増やすこと)をいつ気にすべきか判断できるようになります。

## 同じメモリ、2 通りの歩き方

C の配列 `double u[NY][NX]` は行優先(row-major、右側の添字がメモリ上で連続)です。Fortran の配列 `u(NX, NY)` は列優先(column-major、左側の添字が連続)です。2 つの言語をつなぐと、同じメモリを `u[j][i]` と `u(i,j)` で呼ぶことになります。添字の順序が逆になることは、多くの人が知っています。

見落としやすいのはループ順です。C では `for i { for j { u[i][j] } }` が連続アクセスです。これを Fortran で `do i; do j; u(i,j)` と移すと、内側ループが右側の添字を回ります。列優先配列で右側の添字が 1 違うと、アドレスは N 要素離れます。

$$
\text{addr}(i,j) = (i + j\,\ell_d)\times 8\ \text{bytes}
$$

$\ell_d$ は宣言された第 1 次元の大きさ(leading dimension)、8 は倍精度実数 1 個のバイト数です。$i$ が 1 増えると 8 バイト、$j$ が 1 増えると $8\ell_d$ バイト移動します。

CPU はメモリをキャッシュライン(cache line、一度に読み込む 64 バイトのブロック)単位で取ってきます。倍精度 8 個で 1 ラインです。連続に歩けば 8 回のアクセスでミス(miss、キャッシュになくメモリまで行くアクセス)は 1 回です。ストライド N で歩くと、アクセスごとに新しいラインになります。ただし次の内側ループは同じラインを再び使います。その間ラインがキャッシュに残っていれば損はありません。

キャッシュサイズ(cache)を格子 N 以上にすると、右側(ストライド N)の歩き方でもライン境界の行だけが赤く、残りは緑です。キャッシュを N より 1 本減らすだけで、右側は全部赤に変わります。損失はじわじわではなく、崖のようにやって来ます。

## 原因 1:内側ループが保持すべきライン数

ストライド N の歩き方では、内側ループ 1 回が行 $i$ に沿って N 列を通ります。列ごとに別のラインなので、N 本のラインが必要です。次の $i$ はほとんど同じラインにあり、8 行に 1 回だけ新しいラインが要ります。条件は 1 つです。

$$
N \lesssim N_{\text{lines}} = \frac{C}{L}
$$

$C$ はキャッシュ容量、$L$ はラインサイズです。典型的な L1 データキャッシュは 32 KiB、64 B ラインなので 512 ラインです。5 点ステンシルは $i-1, i, i+1$ の 3 行を使いますが、これらはほぼ同じラインにあります。そのため N が 500 前後を超えると、ストライド N の歩き方はアクセスごとにミスします。

ここまでなら「小さい格子は大丈夫」で終わります。ところが N=256 は 512 より小さいのに遅かったのです。

## 原因 2:2 のべき乗ストライドは少数のセットに集中する

実際のキャッシュはフルアソシアティブ(fully associative、どこにでもラインを置ける構造)ではありません。8-way セットアソシアティブキャッシュは、ラインを 64 個のセットのうち 1 つにしか入れません。セット番号はライン番号を 64 で割った余りです。1 セットには 8 本しか入りません。

$$
\text{set} = \left\lfloor \frac{\text{addr}}{L} \right\rfloor \bmod S,\qquad S_{\text{used}} = \frac{S}{\gcd(8\ell_d/L,\ S)}
$$

$S$ はセット数(64)です。$\ell_d=256$ なら 1 列は 2048 バイト、つまり 32 ラインです。$\gcd(32, 64)=32$ なので、ストライド N の歩き方は 2 セットしか回りません。使える場所は 2×8 = 16 ラインだけです。256 ライン必要なのに 16 ラインに閉じ込められます。キャッシュの 97% が空いているのに追い出され続けます。これが競合ミス(conflict miss)です。

$\ell_d=200$ なら 1 列は 25 ラインです。25 は奇数なので 64 セットすべてを回ります。512 ラインを全部使え、200 ラインは余裕で収まります。

## コード:32 KiB 8-way L1 に 5 点ステンシルを流してミスを数える

実時間を測ると、ハードウェアプリフェッチャ、TLB、OS のノイズが混ざります。そこでキャッシュを直接模倣します。LRU(least recently used、最も長く使われていないラインを追い出す規則)のセットアソシアティブキャッシュに、5 点ステンシルの読み出しアドレスを順に入れます。格子全体ではなく内部 64 行の帯だけを使います。定常状態のミス率は同じで、時間は数十分の一になります。

```python
# 列優先(column-major)配列 u(i,j) を 5 点ステンシルで読むときの L1 キャッシュミスを数える
LINE, WAYS, SIZE = 64, 8, 32 * 1024          # 64 B ライン、8-way、32 KiB(典型的な L1d)
NSETS = SIZE // (LINE * WAYS)                # 64 セット
STRIP = 64                                   # 内部行 i = 1..64 の帯だけをシミュレーション

def stencil_misses(n, ld, i_inner):
    sets = [[] for _ in range(NSETS)]        # セットごとの LRU リスト(末尾が最新)
    miss = 0
    def touch(i, j):
        nonlocal miss
        line = ((i + j * ld) * 8) // LINE    # 列優先アドレス:i が連続
        s = sets[line % NSETS]
        if line in s:
            s.remove(line)
        else:
            miss += 1
            if len(s) == WAYS:
                s.pop(0)                     # 最も古いラインを追い出す
        s.append(line)
    rows, cols = range(1, STRIP + 1), range(1, n - 1)
    order = ((i, j) for j in cols for i in rows) if i_inner else \
            ((i, j) for i in rows for j in cols)
    for i, j in order:
        for di, dj in ((0, 0), (-1, 0), (1, 0), (0, -1), (0, 1)):
            touch(i + di, j + dj)
    return miss / (STRIP * (n - 2))

print(f"L1 {SIZE//1024} KiB, {WAYS}-way, {NSETS} sets, line {LINE} B -> {SIZE//LINE} lines")
print(f"{'N':>5} {'ld':>5} {'i-inner':>8} {'j-inner':>8} {'ratio':>6} {'sets used':>9}")
from math import gcd
for n, ld in [(64,64),(128,128),(128,129),(200,200),(256,256),(256,257),
              (400,401),(480,481),(512,513),(600,601)]:
    a = stencil_misses(n, ld, True)
    b = stencil_misses(n, ld, False)
    stride = ld * 8 // LINE if ld * 8 % LINE == 0 else None
    used = NSETS // gcd(stride, NSETS) if stride else NSETS
    print(f"{n:5d} {ld:5d} {a:8.3f} {b:8.3f} {b/a:6.1f} {used:9d}")
```

既定値 N=256 では、オレンジ(j 内側)のセット図は 2 列だけが光り、ミス率は出力ブロックの 1.258 付近まで上がります。「pad leading dim」をオンにすると 64 セット全体が均等に埋まり、0.144 まで下がります。N を 200・300・384 に動かしたり、連想度を 2-way に下げたりすると、表にない境界がどこにあるかすぐに分かります。

## 数字を読む:0.142、1.258、そして N=400 の 0.340

**i 内側 0.142。** 1 点につき 5 回読みます。そのうち新しいラインが必要なのは $j+1$ 列だけで、8 点に 1 回です。$1/8 = 0.125$ に帯の境界効果が少し乗った値で、N にはほとんど依存しません。

**j 内側 1.258。** 点ごとに $j+1$ 列のラインが新しく入り、上下の行もときどき別のラインに乗ります。1 点あたり 1 を超えます。8.9 倍という比は「1 ラインに要素 8 個」をそのまま失った値です。

**N=64 はなぜ平気か。** 8 セットしか使いませんが、8×8 = 64 ラインが入ります。必要な 64 ラインとちょうど一致します。N=128 は 4 セット、32 ラインしかなく破綻します。2 のべき乗でも小さければ助かります。

**N=400 の 0.340。** パディングでセットは全部使えます。しかし 401 ラインに上下の行のラインが加わると 512 に近づき、LRU が一部を取りこぼします。容量の崖の斜面です。480 からはパディングしても効きません。容量そのものが足りないからです。

## 解決:3 つの手とそれぞれのコスト

**1. ループを入れ替える。** Fortran では一番左の添字を一番内側のループにします。`do j` を外、`do i` を内です。コストはゼロです。ただし C 側の関数とソースを共有していると、どちらかが誤った順序になります。言語境界で配列を渡すときは「どちらが内側か」をインターフェースのコメントに明記しておくのがよいでしょう。

**2. 宣言サイズを 1 つ増やす。** `real(8) :: u(N+1, N)` と宣言し、1..N だけを使います。ストライドが 2 のべき乗から外れ、全セットを使えます。メモリのコストは $1/N$ です。行・列の双方向スイープが混在する ADI(交互方向陰解法)のように、ループ順を変えられない場合にも効きます。ただし表のとおり、N がキャッシュライン数を超えると効果はありません。

**3. ブロッキング(blocking、格子を小さなタイルに分け、タイル単位で回すこと)。** 内側ループの長さをタイル幅 B に縮めれば、必要なライン数は N から B に減ります。N がどれほど大きくても効きます。代わりにコードが複雑になります。[ルーフライン記事](/ja/posts/2026-11-13-roofline-jacobi-gpu-bandwidth-bound/)で見た時間ブロッキングと組み合わせれば、帯域幅の限界も押し広げられます。

順番も大切です。[ホットスポット比率の記事](/ja/posts/2026-11-11-python-hotspot-amdahl-poisson-share/)のように、まずプロファイラでこのループが本当にボトルネックか確かめます。そうであれば 1、だめなら 2、それでも足りなければ 3 です。

## 次の格子サイズを 2 のべき乗にする前に

マルチグリッドや FFT のために格子を $2^k$ にするのはよくあることです。それ自体は問題ではありません。問題は配列の宣言サイズまで $2^k$ に合わせる癖です。計算格子は 256 のまま、宣言だけ 257 にすれば済みます。

点検は 1 行で終わります。1 列のバイト数 $8\ell_d$ を 64 で割ります。その値と 64 の最大公約数が大きければ危険です。32 以上なら 8-way L1 で 16 ライン以下に閉じ込められます。そしてストライド方向に回るループが 1 つでもあるかを確認します。両方に当てはまれば、パディング 1 行が最も安い修正です。
