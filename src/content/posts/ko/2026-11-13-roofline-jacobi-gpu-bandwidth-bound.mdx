## 연산 성능이 15배인데 속도는 4.5배였다

카탈로그상 연산 성능이 15배인 GPU로 Poisson 솔버를 옮겼다. 결과는 4.5배였다. 커널을 다시 짜도, 캐시를 잘 써도 4.5배에서 꿈쩍하지 않았다. 이상한 점은 따로 있다. 4.5는 두 장치의 메모리 대역폭 비율과 소수점까지 같다. 이 글은 그 일치가 우연이 아님을 보인다. 루프라인 모델(roofline model, 연산 성능과 메모리 대역폭 중 더 낮은 쪽이 속도를 정한다는 모델)로 Jacobi 스윕의 한계를 계산한다. 끝까지 읽으면 GPU 이식 전에 기대 속도 향상을 종이 위에서 견적할 수 있다.

## 2020년 노트의 세 줄

2020년 2월 노트에는 CPU와 GPU의 차이가 세 줄로 적혀 있다. CPU는 임의 메모리 접근과 흐름 제어(분기·루프 조건)가 섞인 범용 연산에 맞다. GPU는 많은 데이터에 같은 연산을 반복하는 데이터 병렬 연산에 맞다. 그리고 GPU의 메모리 대역폭이 CPU보다 높다. 예로 든 숫자는 180 GB/s 대 40 GB/s였다.

세 번째 줄이 가장 중요하다. 앞의 두 줄은 "GPU가 잘하는 일"을 말한다. 세 번째 줄은 "그 일이 얼마나 빨라지는가"의 상한을 말한다. CFD의 스텐실 연산(stencil, 주변 격자점 몇 개로 한 점을 갱신하는 계산)은 데이터 병렬의 전형이다. 그래서 GPU에 잘 맞는다. 하지만 얼마나 빨라지는지는 대역폭이 정한다.

## 루프라인: 성능은 두 천장 중 낮은 쪽

커널 하나의 실제 성능 $P$는 다음 식으로 묶인다.

$$
P = \min\left(P_{\text{peak}},\; I \cdot B\right), \qquad I = \frac{\text{FLOP}}{\text{byte}}
$$

$P_{\text{peak}}$는 장치의 최대 연산 성능(FLOP/s), $B$는 메모리 대역폭(byte/s)이다. $I$는 산술 강도(arithmetic intensity, DRAM에서 1바이트를 가져올 때마다 하는 연산 수)다.

로그-로그 그래프에서 이 식은 기울어진 직선과 수평선이 만나는 지붕 모양이 된다. 두 선이 만나는 $I^* = P_{\text{peak}}/B$를 능선점(ridge point)이라 부른다. $I < I^*$이면 연산 장치가 데이터를 기다린다. 이를 메모리 한계(memory-bound)라 한다. $I > I^*$이면 데이터는 충분하고 연산이 병목이다. 이를 연산 한계(compute-bound)라 한다.

이 글의 장치 모델은 노트의 대역폭을 그대로 쓰고 최대 성능은 가정했다. CPU는 40 GB/s, 300 GFLOP/s다. GPU는 180 GB/s, 4,500 GFLOP/s다. 능선점은 CPU 7.5, GPU 25.0이다. 두 장치 모두 $I < 7.5$인 커널은 대역폭만 본다. 그런 커널의 속도 향상은 $180/40 = 4.5$배다.

## Jacobi 스윕 한 번이 옮기는 바이트

2차원 Poisson 방정식 $-\nabla^2 u = f$의 Jacobi 갱신은 다음과 같다.

$$
u^{k+1}_{i,j} = \tfrac14\left(u^k_{i-1,j} + u^k_{i+1,j} + u^k_{i,j-1} + u^k_{i,j+1} + h^2 f_{i,j}\right)
$$

$h$는 격자 간격, $k$는 반복 번호다. 셀 하나당 덧셈 4번, 곱셈 1번이 든다. 수렴 판정용 $|\Delta u|$ 비교 1번을 더해 6 FLOP으로 센다.

바이트는 캐시 재사용에 따라 달라진다. 이웃 4개와 $f$를 매번 DRAM에서 읽고 결과를 쓰면 배정밀도로 $6 \times 8 = 48$바이트다. 캐시가 이웃 값을 재사용하면 $u$ 읽기, $f$ 읽기, $u^{k+1}$ 쓰기만 남아 24바이트다. 산술 강도는 각각 0.125와 0.25다. 둘 다 CPU 능선점 7.5보다 30배 이상 작다. 캐시를 아무리 잘 써도 이 커널은 메모리 한계를 벗어나지 못한다.

여기서 반복 수가 끼어든다. 총시간은 "스윕 1회 시간 × 스윕 수"다. 스윕 수는 하드웨어가 아니라 알고리즘이 정한다. Jacobi의 스펙트럼 반경은 $1 - \pi^2 h^2/2$ 근처다. 격자를 두 배로 하면 스윕 수는 이론상 4배, 이 글의 판정 기준으로는 약 3배가 된다.

## 코드: 실제로 스윕을 세고 두 장치에 시간을 매긴다

아래 코드는 단위 정사각형에서 $-\nabla^2 u = 1$을 Jacobi로 푼다. 스윕 수는 실제로 세고, 시간은 루프라인 식으로 매긴다. 커널은 바이트 수만 다르게 여섯 가지를 비교한다. 시간 블로킹(temporal blocking, 캐시에 올린 타일에서 스윕 $k$번을 연달아 돌려 DRAM 왕복을 $1/k$로 줄이는 기법)과 매 스윕 PCIe 복사도 넣었다.

```python
import numpy as np

# 장치 모델: 원본 노트의 대역폭(40 vs 180 GB/s) + 가정한 최대 연산 성능
DEV = {"CPU": (40e9, 300e9), "GPU": (180e9, 4500e9)}   # (B/s, FLOP/s)
PCIE = 12e9                                            # 호스트<->GPU 복사 대역폭

def jacobi_sweeps(n, tol=1e-6):
    """단위 정사각형 -∇²u = 1, u=0 경계. max|Δu| < tol 까지 Jacobi 스윕 수."""
    h2 = (1.0 / (n - 1)) ** 2
    u = np.zeros((n, n))
    for it in range(1, 10**6):
        new = 0.25 * (u[:-2, 1:-1] + u[2:, 1:-1] + u[1:-1, :-2] + u[1:-1, 2:] + h2)
        du = np.abs(new - u[1:-1, 1:-1]).max()
        u[1:-1, 1:-1] = new
        if du < tol:
            return it

def roofline_time(cells, sweeps, flops, bytes_, dev, pcie_bytes=0.0):
    bw, peak = DEV[dev]
    per_sweep = cells * max(flops / peak, bytes_ / bw)
    return sweeps * (per_sweep + cells * pcie_bytes / PCIE)

FLOPS = 6.0   # 셀당: 덧셈 4 + 곱 1 + |Δu| 비교 1
KERNELS = [   # (이름, 셀당 DRAM 바이트, 셀당 PCIe 바이트)
    ("naive (no reuse)", 48.0, 0.0),
    ("cached u,f,u_new", 24.0, 0.0),
    ("temporal block k=4", 24.0 / 4, 0.0),
    ("temporal block k=32", 24.0 / 32, 0.0),
    ("temporal block k=128", 24.0 / 128, 0.0),
    ("cached + PCIe copy/sweep", 24.0, 16.0),
]

for n in (32, 64, 128):
    print(f"N={n:4d}  sweeps={jacobi_sweeps(n):6d}")

n = 64
sweeps = jacobi_sweeps(n)
cells = (n - 2) ** 2
print(f"\nN={n}, sweeps={sweeps}, ridge CPU={300/40:.1f}  GPU={4500/180:.1f} FLOP/B")
print(f"{'kernel':26s} {'AI':>6s} {'CPU ms':>8s} {'GPU ms':>8s} {'speedup':>8s}  bound(GPU)")
for name, b, pb in KERNELS:
    ai = FLOPS / b
    tc = roofline_time(cells, sweeps, FLOPS, b, "CPU") * 1e3
    tg = roofline_time(cells, sweeps, FLOPS, b, "GPU", pb) * 1e3
    bound = "memory" if ai < 4500 / 180 else "compute"
    if pb: bound = "PCIe"
    print(f"{name:26s} {ai:6.3f} {tc:8.3f} {tg:8.3f} {tc/tg:8.2f}  {bound}")
print(f"\npeak FLOP ratio = {4500/300:.1f}x, bandwidth ratio = {180/40:.2f}x")
```


## 4.50이 네 번, 15.00과 0.41이 한 번씩 나온 이유

naive, cached, k=4는 모두 4.50배다. 바이트를 48에서 6으로 8배 줄였더니 두 장치의 시간이 똑같이 8배 줄었다. 비율은 변하지 않는다. 메모리 한계 영역에서는 바이트 절약이 두 장치에 공평하게 돌아가기 때문이다.

k=32에서는 AI가 8이 된다. CPU는 능선점 7.5를 넘어 연산 한계에 걸린다. GPU는 아직 대역폭 영역이다. 그래서 비율이 4.80으로 조금 오른다. k=128에서 AI가 32가 되면 GPU도 능선점 25를 넘는다. 비율은 최대 성능비 15.00에 도달한다. 단, 스윕 128번을 캐시에서 연달아 돌리는 시간 블로킹은 현실적이지 않다. 타일 경계의 고스트 영역이 블로킹 깊이만큼 커지기 때문이다. 이 행은 "15배는 이만큼의 산술 강도가 있어야 나온다"는 눈금으로 읽어야 한다.

마지막 행은 0.41배, 즉 GPU가 2.4배 느리다. 매 스윕마다 필드를 호스트로 보내고 다시 받으면 셀당 16바이트가 12 GB/s 버스를 지난다. 이 버스는 CPU 메모리보다 느리다. 수렴 판정을 호스트에서 하려고 매번 복사하는 코드가 정확히 이 함정에 빠진다. 판정에 필요한 최댓값 하나만 GPU에서 리덕션(reduction, 배열을 한 값으로 줄이는 연산)해 가져오면 이 비용은 사라진다.

첫 표의 N=32, 64, 128 행은 스윕 수가 1,176 → 3,720 → 10,537로 늘어남을 보여준다. 격자를 두 배로 하면 셀은 4배, 스윕은 약 3배가 된다. 장치를 바꿔 얻는 4.5배는 격자 한 단계 세분화에 금방 먹힌다.

## 대역폭 벽 앞에서 쓸 수 있는 세 가지 수

첫째, 바이트를 줄인다. 배정밀도를 단정밀도로 바꾸면 셀당 바이트가 절반이 된다. 메모리 한계 커널은 그만큼 빨라진다. 반복법 내부만 단정밀도로 돌리고 잔차는 배정밀도로 계산하는 혼합 정밀도가 흔한 타협이다.

둘째, 산술 강도를 올린다. 시간 블로킹 외에도 고차 스텐실이나 행렬 없는(matrix-free) 고차 DG 커널은 같은 데이터로 더 많이 계산한다. 이런 커널은 GPU 능선점 쪽으로 이동한다. 그때부터 최대 성능비가 의미를 갖기 시작한다.

셋째, 스윕 수 자체를 줄인다. 다중격자(multigrid)는 스윕 수를 격자 크기와 거의 무관하게 만든다. 이것은 장치 교체로 얻는 4.5배보다 훨씬 크다. 같은 결론을 Amdahl 관점에서 본 글이 있다([핫스팟 비율 p를 정하는 것은 허용오차다](/ko/posts/2026-11-11-python-hotspot-amdahl-poisson-share/)). 음해법에서 반복 수를 정하는 다른 요인은 [LU-SGS의 CFL 수렴 한계](/ko/posts/2026-11-06-lu-sgs-factorization-error-cfl-limit/)에서 다뤘다.

## GPU 이식 견적서 첫 줄에 적을 숫자

커널마다 셀당 FLOP과 셀당 바이트를 세어 나눈다. 그 값이 두 장치의 능선점보다 작으면 기대 속도 향상은 대역폭비다. 연산 성능비는 견적서에 적지 않는다. 그다음 매 반복 호스트와 주고받는 바이트가 있는지 확인한다. 하나라도 있으면 그 버스 대역폭이 새 천장이 된다. 이 두 줄이면 이식 전에 4.5배인지 0.4배인지 알 수 있다.
