## C 코드를 포트란으로 옮겼더니 격자 크기에 따라 속도가 널뛰었다

2020년 2월, C 코드와 포트란 코드를 한 프로그램으로 합치는 작업을 했다. 그때 노트는 짧다. "CPU는 임의의 메모리 접근에 강하다. GPU는 대역폭이 높다." 실제로 부딪힌 문제는 그 한 줄 사이에 있었다. C에서 쓰던 이중 루프를 포트란으로 그대로 옮겼다. 결과는 맞았다. 그런데 격자 200에서는 빠르고, 격자 256에서는 눈에 띄게 느렸다.

이 글은 그 원인을 캐시 시뮬레이터로 직접 센다. 결론부터 적는다. 루프 순서가 틀리면 느려지는 것은 맞다. 하지만 언제 느려지는지는 격자 크기가 정한다. 그리고 2의 거듭제곱 크기는 특히 위험하다. 읽고 나면 루프 순서와 배열 패딩(padding, 배열 선언 크기를 일부러 한 칸 늘리는 것)을 언제 신경 써야 하는지 판단할 수 있다.

## 같은 메모리, 두 가지 걷는 법

C 배열 `double u[NY][NX]`는 행 우선(row-major, 오른쪽 첨자가 메모리에서 연속)이다. 포트란 배열 `u(NX, NY)`는 열 우선(column-major, 왼쪽 첨자가 연속)이다. 두 언어를 합칠 때 같은 메모리를 `u[j][i]`와 `u(i,j)`로 부르게 된다. 첨자 순서가 뒤집히는 것까지는 다들 안다.

놓치기 쉬운 것은 루프 순서다. C에서는 `for i { for j { u[i][j] } }`가 연속 접근이다. 이것을 포트란에서 `do i; do j; u(i,j)`로 옮기면 안쪽 루프가 오른쪽 첨자를 돈다. 열 우선 배열에서 오른쪽 첨자 하나 차이는 주소로 N칸이다.

$$
\text{addr}(i,j) = (i + j\,\ell_d)\times 8\ \text{bytes}
$$

$\ell_d$는 선언된 첫 차원 크기(leading dimension), 8은 배정밀도 실수 하나의 바이트 수다. $i$가 1 늘면 8바이트, $j$가 1 늘면 $8\ell_d$바이트 이동한다.

CPU는 메모리를 캐시 라인(cache line, 한 번에 가져오는 64바이트 블록) 단위로 가져온다. 배정밀도 8개가 한 라인이다. 연속으로 걸으면 8번 접근에 미스(miss, 캐시에 없어 메모리까지 가는 접근) 1번이다. 보폭 N으로 걸으면 접근마다 새 라인이다. 다만 다음 안쪽 루프가 같은 라인들을 다시 쓴다. 그 사이 라인들이 캐시에 살아남으면 손해가 없다.

캐시 크기(cache)를 격자 N 이상으로 두면 오른쪽(보폭 N) 걷기도 라인 경계 행만 빨갛고 나머지는 초록이다. 캐시를 N보다 한 칸만 줄여도 오른쪽은 전부 빨간색으로 바뀐다. 손해는 서서히 오지 않고 절벽처럼 온다.

## 원인 1: 안쪽 루프가 붙잡아야 하는 라인 수

보폭 N 걷기에서 안쪽 루프 하나는 행 $i$를 따라 N개 열을 지난다. 열마다 다른 라인이니 라인 N개가 필요하다. 다음 $i$는 대부분 같은 라인에 있다. 8행마다 한 번만 새 라인이 필요하다. 그래서 조건은 하나다.

$$
N \lesssim N_{\text{lines}} = \frac{C}{L}
$$

$C$는 캐시 용량, $L$은 라인 크기다. 전형적인 L1 데이터 캐시는 32 KiB, 64 B 라인이니 512라인이다. 5점 스텐실은 $i-1, i, i+1$ 세 행을 함께 쓰지만 이들은 거의 같은 라인에 있다. 그래서 N이 500 언저리를 넘으면 보폭 N 걷기는 접근마다 미스가 난다.

여기까지면 "작은 격자는 괜찮다"로 끝난다. 그런데 N=256은 512보다 작은데도 느렸다.

## 원인 2: 2의 거듭제곱 보폭은 세트 몇 개에 몰린다

실제 캐시는 완전 연관(fully associative, 아무 자리에나 라인을 둘 수 있는 구조)이 아니다. 8-way 집합 연관(set-associative) 캐시는 라인을 64개 세트(set) 중 하나에만 넣는다. 세트 번호는 라인 번호를 64로 나눈 나머지다. 세트 하나에는 8개만 들어간다.

$$
\text{set} = \left\lfloor \frac{\text{addr}}{L} \right\rfloor \bmod S,\qquad S_{\text{used}} = \frac{S}{\gcd(8\ell_d/L,\ S)}
$$

$S$는 세트 수(64)다. $\ell_d=256$이면 열 하나가 2048바이트, 즉 32라인이다. $\gcd(32, 64)=32$이니 보폭 N 걷기는 세트 2개만 돈다. 쓸 수 있는 자리는 2×8 = 16라인뿐이다. 256라인이 필요한데 16라인에 갇힌다. 캐시의 97%가 비어 있는데도 계속 쫓겨난다. 이것이 충돌 미스(conflict miss)다.

$\ell_d=200$이면 열 하나가 25라인이다. 25는 홀수라 64개 세트를 모두 돈다. 512라인 전부를 쓸 수 있고 200라인은 여유 있게 들어간다.

## 코드: 32 KiB 8-way L1에 5점 스텐실을 흘려 미스를 센다

실제 시간을 재면 하드웨어 프리페처, TLB, 운영체제 잡음이 섞인다. 그래서 캐시를 직접 흉내 낸다. LRU(least recently used, 가장 오래 안 쓴 라인을 내보내는 규칙) 집합 연관 캐시에 5점 스텐실의 읽기 주소를 순서대로 넣는다. 전체 격자 대신 내부 64행짜리 띠만 쓴다. 정상 상태 미스율은 같고 시간은 수십 배 줄어든다.

```python
# 열 우선(column-major) 배열 u(i,j)를 5점 스텐실로 읽을 때 L1 캐시 미스를 센다
LINE, WAYS, SIZE = 64, 8, 32 * 1024          # 64 B 라인, 8-way, 32 KiB (전형적 L1d)
NSETS = SIZE // (LINE * WAYS)                # 64 세트
STRIP = 64                                   # 내부 행 i = 1..64 띠만 시뮬레이션

def stencil_misses(n, ld, i_inner):
    sets = [[] for _ in range(NSETS)]        # 세트별 LRU 목록 (뒤가 최근)
    miss = 0
    def touch(i, j):
        nonlocal miss
        line = ((i + j * ld) * 8) // LINE    # 열 우선 주소: i가 연속
        s = sets[line % NSETS]
        if line in s:
            s.remove(line)
        else:
            miss += 1
            if len(s) == WAYS:
                s.pop(0)                     # 가장 오래된 라인 축출
        s.append(line)
    rows, cols = range(1, STRIP + 1), range(1, n - 1)
    order = ((i, j) for j in cols for i in rows) if i_inner else \
            ((i, j) for i in rows for j in cols)
    for i, j in order:
        for di, dj in ((0, 0), (-1, 0), (1, 0), (0, -1), (0, 1)):
            touch(i + di, j + dj)
    return miss / (STRIP * (n - 2))

print(f"L1 {SIZE//1024} KiB, {WAYS}-way, {NSETS} sets, line {LINE} B -> {SIZE//LINE} lines")
print(f"{'N':>5} {'ld':>5} {'i-inner':>8} {'j-inner':>8} {'ratio':>6} {'sets used':>9}")
from math import gcd
for n, ld in [(64,64),(128,128),(128,129),(200,200),(256,256),(256,257),
              (400,401),(480,481),(512,513),(600,601)]:
    a = stencil_misses(n, ld, True)
    b = stencil_misses(n, ld, False)
    stride = ld * 8 // LINE if ld * 8 % LINE == 0 else None
    used = NSETS // gcd(stride, NSETS) if stride else NSETS
    print(f"{n:5d} {ld:5d} {a:8.3f} {b:8.3f} {b/a:6.1f} {used:9d}")
```

```text
   64    64    0.129    0.129    1.0         8
  128   128    0.143    1.266    8.9         4
  128   129    0.145    0.145    1.0        64

  256   257    0.144    0.144    1.0        64

```

기본값 N=256에서 주황색(j 안쪽) 세트 막대는 두 칸만 번쩍인다. 미스율은 출력 블록의 1.258 근처로 올라간다. "pad leading dim"을 켜면 64칸 전체가 고르게 차고 0.144로 내려온다. N을 200·300·384로 옮겨 보거나 연관도를 2-way로 낮춰 보면, 표에 없는 경계가 어디인지 바로 보인다.

## 숫자 읽기: 0.142, 1.258, 그리고 400에서의 0.340

**i 안쪽 0.142.** 점 하나에 다섯 번 읽는다. 그중 새 라인이 필요한 것은 $j+1$ 열뿐이고 8점에 한 번이다. $1/8 = 0.125$에 띠 경계 효과가 조금 붙었다. 이 값은 N에 거의 무관하다.

**j 안쪽 1.258.** 점마다 $j+1$ 열의 라인이 새로 들어오고, 위아래 행도 가끔 다른 라인을 탄다. 점당 1이 넘는다. 비율 8.9배는 "라인당 원소 8개"를 그대로 잃은 값이다.

**N=64는 왜 멀쩡한가.** 세트 8개만 쓰지만 8×8 = 64라인이 들어간다. 필요한 64라인과 딱 맞는다. N=128은 세트 4개, 32라인뿐이라 터진다. 2의 거듭제곱이라도 작으면 산다.

**N=400의 0.340.** 패딩해서 세트는 다 쓴다. 하지만 401라인에 위아래 행 라인까지 얹히면 512에 가까워진다. LRU가 일부를 놓친다. 용량 절벽의 경사면이다. 480부터는 패딩해도 소용없다. 이때는 용량 자체가 모자라다.

## 해결: 세 가지 수와 각각의 비용

**1. 루프를 뒤집는다.** 포트란에서는 가장 왼쪽 첨자를 가장 안쪽 루프로 둔다. `do j` 바깥, `do i` 안쪽이다. 비용은 0이다. 하지만 C 쪽 함수와 같은 소스를 공유하면 한쪽은 틀린 순서가 된다. 언어 경계에서 배열을 넘길 때 "누가 안쪽인가"를 인터페이스 주석에 박아 두는 것이 좋다.

**2. 선언 크기를 한 칸 늘린다.** `real(8) :: u(N+1, N)`으로 잡고 1..N만 쓴다. 보폭이 2의 거듭제곱에서 벗어나 모든 세트를 쓴다. 메모리 비용은 $1/N$이다. 루프 순서를 바꿀 수 없는 경우, 예를 들어 행·열 양방향 스윕이 섞인 ADI(교대 방향 음해법)에도 통한다. 단 위 표처럼 N이 캐시 라인 수를 넘으면 효과가 없다.

**3. 블로킹(blocking, 격자를 작은 타일로 나눠 타일 단위로 도는 것).** 안쪽 루프 길이를 타일 폭 B로 줄이면 필요한 라인 수가 N에서 B로 준다. N이 아무리 커도 통한다. 대신 코드가 복잡해진다. [루프라인 글](/ko/posts/2026-11-13-roofline-jacobi-gpu-bandwidth-bound/)에서 본 시간 블로킹과 결합하면 대역폭 한계도 함께 밀어낼 수 있다.

순서도 중요하다. [핫스팟 비율 글](/ko/posts/2026-11-11-python-hotspot-amdahl-poisson-share/)처럼 먼저 프로파일러로 이 루프가 실제 병목인지 확인한다. 병목이면 1번, 안 되면 2번, 그래도 모자라면 3번이다.

## 다음 격자 크기를 2의 거듭제곱으로 잡기 전에

멀티그리드(multigrid)나 FFT 때문에 격자를 $2^k$로 잡는 일은 흔하다. 그것 자체는 문제가 아니다. 문제는 배열 선언 크기까지 $2^k$로 맞추는 습관이다. 계산 격자는 256으로 두고 선언만 257로 하면 된다.

점검은 한 줄이면 끝난다. 열 하나의 바이트 수 $8\ell_d$를 64로 나눈다. 그 값과 64의 최대공약수가 크면 위험하다. 32 이상이면 8-way L1에서 16라인 이하에 갇힌다. 그리고 보폭 방향으로 도는 루프가 하나라도 있는지 본다. 둘 다 해당하면 패딩 한 칸이 가장 싼 수정이다.
