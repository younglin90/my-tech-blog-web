## 15x the compute, 4.5x the speed

We moved a Poisson solver to a GPU whose spec sheet promised 15 times the compute. We got 4.5x. Rewriting the kernel didn't move it. Better cache use didn't move it either. Here is the odd part: 4.5 matches the ratio of the two devices' memory bandwidths to the decimal point. This post shows that the match is no accident. We use the roofline model (a model saying that whichever is lower, compute throughput or memory bandwidth, sets the speed) to compute the limit of a Jacobi sweep. By the end you can estimate the speedup of a GPU port on paper, before writing any CUDA.

## Three lines from a 2020 note

A note from February 2020 sums up CPU versus GPU in three lines. CPUs suit general-purpose work with random memory access and control flow (branches, loop conditions). GPUs suit data-parallel work that applies the same operation to lots of data. And GPU memory bandwidth is higher than CPU bandwidth. The example numbers were 180 GB/s versus 40 GB/s.

The third line matters most. The first two say what a GPU is good at. The third sets the ceiling on how much faster that work gets. CFD stencil operations (updating a point from a few neighboring grid points) are textbook data parallelism. So they fit GPUs well. But how much faster they run is decided by bandwidth.

## Roofline: performance is the lower of two ceilings

The attained performance $P$ of a kernel is bounded by:

$$
P = \min\left(P_{\text{peak}},\; I \cdot B\right), \qquad I = \frac{\text{FLOP}}{\text{byte}}
$$

$P_{\text{peak}}$ is the device's peak compute (FLOP/s) and $B$ its memory bandwidth (byte/s). $I$ is the arithmetic intensity (the number of operations performed per byte fetched from DRAM).

On a log-log plot this is a sloped line meeting a flat one, like a roof. The meeting point $I^* = P_{\text{peak}}/B$ is the ridge point. For $I < I^*$ the compute units wait on data. That is memory-bound. For $I > I^*$ data arrives fast enough and compute is the bottleneck. That is compute-bound.

Our device model keeps the note's bandwidths and assumes the peaks. The CPU has 40 GB/s and 300 GFLOP/s. The GPU has 180 GB/s and 4,500 GFLOP/s. The ridge points are 7.5 for the CPU and 25.0 for the GPU. Any kernel with $I < 7.5$ sees only bandwidth on both devices. Its speedup is $180/40 = 4.5$.

## Bytes moved by one Jacobi sweep

The Jacobi update for the 2D Poisson equation $-\nabla^2 u = f$ is:

$$
u^{k+1}_{i,j} = \tfrac14\left(u^k_{i-1,j} + u^k_{i+1,j} + u^k_{i,j-1} + u^k_{i,j+1} + h^2 f_{i,j}\right)
$$

$h$ is the grid spacing and $k$ the iteration index. Each cell costs 4 additions and 1 multiplication. Add 1 comparison of $|\Delta u|$ for the convergence check and we count 6 FLOPs.

The byte count depends on cache reuse. Reading four neighbors and $f$ from DRAM and writing the result costs $6 \times 8 = 48$ bytes in double precision. If the cache reuses neighbor values, only the read of $u$, the read of $f$, and the write of $u^{k+1}$ remain: 24 bytes. The arithmetic intensities are 0.125 and 0.25. Both sit more than 30 times below the CPU ridge of 7.5. No matter how well you use the cache, this kernel stays memory-bound.

Then the iteration count enters. Total time is "time per sweep × number of sweeps." The sweep count is set by the algorithm, not the hardware. Jacobi's spectral radius is near $1 - \pi^2 h^2/2$. Doubling the grid multiplies the sweep count by 4 in theory and by about 3 under this post's stopping test.

## Code: count real sweeps, then charge each device

The code below solves $-\nabla^2 u = 1$ on the unit square with Jacobi. It really counts the sweeps and charges time with the roofline formula. Six kernels differ only in byte count. We include temporal blocking (running $k$ sweeps back to back on a cache-resident tile, cutting DRAM round trips to $1/k$) and a PCIe copy every sweep.

```python
import numpy as np

# Device model: bandwidths from the original note (40 vs 180 GB/s) + assumed peak compute
DEV = {"CPU": (40e9, 300e9), "GPU": (180e9, 4500e9)}   # (B/s, FLOP/s)
PCIE = 12e9                                            # host<->GPU copy bandwidth

def jacobi_sweeps(n, tol=1e-6):
    """Unit square, -∇²u = 1, u=0 on walls. Jacobi sweeps until max|Δu| < tol."""
    h2 = (1.0 / (n - 1)) ** 2
    u = np.zeros((n, n))
    for it in range(1, 10**6):
        new = 0.25 * (u[:-2, 1:-1] + u[2:, 1:-1] + u[1:-1, :-2] + u[1:-1, 2:] + h2)
        du = np.abs(new - u[1:-1, 1:-1]).max()
        u[1:-1, 1:-1] = new
        if du < tol:
            return it

def roofline_time(cells, sweeps, flops, bytes_, dev, pcie_bytes=0.0):
    bw, peak = DEV[dev]
    per_sweep = cells * max(flops / peak, bytes_ / bw)
    return sweeps * (per_sweep + cells * pcie_bytes / PCIE)

FLOPS = 6.0   # per cell: 4 adds + 1 mul + 1 |Δu| compare
KERNELS = [   # (name, DRAM bytes per cell, PCIe bytes per cell)
    ("naive (no reuse)", 48.0, 0.0),
    ("cached u,f,u_new", 24.0, 0.0),
    ("temporal block k=4", 24.0 / 4, 0.0),
    ("temporal block k=32", 24.0 / 32, 0.0),
    ("temporal block k=128", 24.0 / 128, 0.0),
    ("cached + PCIe copy/sweep", 24.0, 16.0),
]

for n in (32, 64, 128):
    print(f"N={n:4d}  sweeps={jacobi_sweeps(n):6d}")

n = 64
sweeps = jacobi_sweeps(n)
cells = (n - 2) ** 2
print(f"\nN={n}, sweeps={sweeps}, ridge CPU={300/40:.1f}  GPU={4500/180:.1f} FLOP/B")
print(f"{'kernel':26s} {'AI':>6s} {'CPU ms':>8s} {'GPU ms':>8s} {'speedup':>8s}  bound(GPU)")
for name, b, pb in KERNELS:
    ai = FLOPS / b
    tc = roofline_time(cells, sweeps, FLOPS, b, "CPU") * 1e3
    tg = roofline_time(cells, sweeps, FLOPS, b, "GPU", pb) * 1e3
    bound = "memory" if ai < 4500 / 180 else "compute"
    if pb: bound = "PCIe"
    print(f"{name:26s} {ai:6.3f} {tc:8.3f} {tg:8.3f} {tc/tg:8.2f}  {bound}")
print(f"\npeak FLOP ratio = {4500/300:.1f}x, bandwidth ratio = {180/40:.2f}x")
```

## Why 4.50 shows up four times, and 15.00 and 0.41 once each

Naive, cached, and k=4 all give 4.50x. Cutting bytes 8x, from 48 to 6, cut both devices' times by exactly 8x. The ratio did not change. In the memory-bound regime, byte savings pay both devices equally.

At k=32 the AI is 8. The CPU passes its ridge of 7.5 and becomes compute-bound. The GPU is still bandwidth-limited. So the ratio rises slightly to 4.80. At k=128 the AI is 32 and the GPU also passes its ridge of 25. The ratio reaches the 15.00 peak FLOP ratio. Note that blocking 128 sweeps in cache is not realistic. The ghost region at tile edges grows with blocking depth. Read that row as a ruler: "15x needs this much arithmetic intensity."

The last row is 0.41x, meaning the GPU is 2.4 times slower. Sending the field to the host and back every sweep pushes 16 bytes per cell through a 12 GB/s bus. That bus is slower than CPU memory. Code that copies everything back just to test convergence on the host falls into exactly this trap. Doing a reduction (collapsing an array into one value) on the GPU and fetching just the maximum removes this cost.

The first table, with N=32, 64, 128, shows sweeps growing 1,176 → 3,720 → 10,537. Doubling the grid gives 4x the cells and about 3x the sweeps. The 4.5x you gain by switching devices is quickly eaten by one level of refinement.

## Three moves against the bandwidth wall

First, move fewer bytes. Switching from double to single precision halves the bytes per cell. A memory-bound kernel speeds up by the same factor. A common compromise is mixed precision: iterate in single precision and compute residuals in double.

Second, raise arithmetic intensity. Besides temporal blocking, high-order stencils and matrix-free high-order DG kernels compute more per byte. They move toward the GPU's ridge point. From there on, the peak FLOP ratio starts to matter.

Third, cut the number of sweeps. Multigrid makes the sweep count almost independent of grid size. That beats the 4.5x from a device swap by a wide margin. A companion post reaches the same conclusion through Amdahl's law ([tolerance sets the hotspot fraction p](/en/posts/2026-11-11-python-hotspot-amdahl-poisson-share/)). Another factor that sets iteration counts in implicit solvers is covered in [the CFL convergence limit of LU-SGS](/en/posts/2026-11-06-lu-sgs-factorization-error-cfl-limit/).

## The first number on a GPU porting estimate

For each kernel, count FLOPs per cell and bytes per cell, and divide. If the result is below both devices' ridge points, the expected speedup is the bandwidth ratio. Leave the peak FLOP ratio off the estimate. Next, check whether any bytes cross between host and device every iteration. If even one does, that bus bandwidth becomes the new ceiling. These two lines tell you before porting whether you are getting 4.5x or 0.4x.
